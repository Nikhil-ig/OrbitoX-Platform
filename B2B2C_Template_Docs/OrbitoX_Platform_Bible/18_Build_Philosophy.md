# Part 18 — Build Philosophy
### *How to Think About Building on OrbitoX — Assembly, Not Construction*

---

## The Mental Model Shift

Traditional software development thinking:

```
"I need to build a School Management System."
↓
Design the schema
↓
Write Auth
↓
Write User management
↓
Write Notifications
↓
Write Reports
↓
Write Dashboard
↓
Write Billing
↓
Write Attendance module
↓
Write Grading module
↓
Write Student management
↓
Write Teacher management
↓
... 6 months later ...
↓
Launch
```

OrbitoX thinking:

```
"I need to build a School Management System."
↓
What does a School Management System need?

  Authentication?        → Platform Core (already done)
  Multi-tenancy?         → Platform Core (already done)
  User management?       → Platform Core (already done)
  Notifications?         → Platform Service (already done)
  Reports?               → Platform Service (already done)
  Dashboard?             → Dynamic UI Engine (already done)
  Billing?               → Platform Core (already done)
  Workflow automation?   → Workflow Engine (already done)
  AI features?           → AI Capability (already done)

  Attendance module?     → Install @orbitox/attendance OR build it
  Grading module?        → Build it (domain-specific)
  Student management?    → Build it (domain-specific)
  Teacher management?    → Build it (domain-specific)

↓
orbitox create school
↓
2-3 weeks for domain-specific logic only
↓
Launch
```

**Only the last 20% is custom. The first 80% is assembled.**

## The Assembly Model

```
Platform Assembly:

@orbitox/core             (authentication, context, RBAC, billing, storage)
  +
@orbitox/services         (AI, notifications, search, reports, files)
  +
@orbitox/attendance       (attendance tracking — reusable across school/workplace)
  +
@orbitox/grading          (grade management — school-specific)
  +
@school/students          (your custom plugin — student profiles)
  +
@school/teachers          (your custom plugin — teacher management)
  +
@school/fees              (your custom plugin — fee collection)

= School Management System
```

The same `@orbitox/attendance` plugin that powers the school system can be installed in an HR system. You don't build attendance twice.

```bash
# 1. Scaffold the product
orbitox create restaurant

# CLI prompts:
✔ Authentication (core)? Yes
✔ Multi-tenancy (core)? Yes
✔ Billing (core)? Yes
✔ AI features? Yes
✔ Notifications (email/SMS/WhatsApp)? Yes
✔ Reports & exports? Yes
✔ Workflow automation? Yes
✔ Install @orbitox/pos (Point of Sale)? Yes
✔ Install @orbitox/inventory? Yes

# Generated:
apps/restaurant/
  plugins/
    menu-management/      # scaffold generated — fill in the domain logic
    table-management/     # scaffold generated
    kitchen-orders/       # scaffold generated
    reservations/         # scaffold generated
```

### What Was Generated vs. What You Write

```
Generated by platform (you write nothing):
  ✅ Auth system
  ✅ User management
  ✅ Role management
  ✅ Multi-tenant isolation
  ✅ Billing & subscriptions
  ✅ Email/SMS/WhatsApp notifications
  ✅ Dashboard framework
  ✅ Report builder
  ✅ AI assistant interface
  ✅ Workflow engine
  ✅ Audit logging
  ✅ Search
  ✅ File uploads

Installed from marketplace (you configure, not code):
  ✅ POS (Point of Sale) — @orbitox/pos
  ✅ Inventory management — @orbitox/inventory

You write (domain-specific business logic only):
  🖊 Menu management (items, categories, pricing, modifiers)
  🖊 Table management (floor plan, reservation linkage)
  🖊 Kitchen display system (KDS) integration
  🖊 Reservation flow
  🖊 Restaurant-specific reporting
```

**80% assembled. 20% custom.**

## Decision Framework: Core vs. Plugin vs. Config

Before writing any code, ask these questions in order:

### Q1: Does the platform already do this?

```
"I need to send notifications when an order is placed."
→ Platform has NotificationCapability
→ Answer: Use the capability. Write zero notification code.
```

### Q2: Does a marketplace plugin already do this?

```
"I need inventory management."
→ @orbitox/inventory exists in marketplace
→ Answer: Install it. Configure it. Write zero inventory code.
```

### Q3: Can this be configuration instead of code?

```
"I need a form for collecting customer allergy information."
→ Metadata Engine + Dynamic Forms can do this
→ Admin adds a custom field: 'Allergies' (textarea)
→ Answer: Store as config. Write zero form code.
```

### Q4: Can this be a workflow instead of code?

```
"When a reservation is confirmed, send a WhatsApp reminder 2 hours before."
→ Workflow Engine handles this
→ Trigger: reservation.confirmed → Delay: 2h → Action: send_whatsapp
→ Answer: Configure a workflow. Write zero automation code.
```

### Q5: Now write the minimum domain-specific code needed.

```
"I need a kitchen display system — orders appear on a screen in real time."
→ No platform capability for this
→ No marketplace plugin for this
→ Cannot be just configuration
→ Answer: Build a KDS plugin. This is the 20% you write.
```

## Plugin Development Flow

```
1. Scaffold
   orbitox new plugin menu-management

2. Define your entities (metadata)
   entities/menu-item.json
   entities/category.json

3. Write only the non-trivial business logic
   services/menu.service.ts
   services/pricing.service.ts   # complex pricing rules

4. Register events your plugin emits
   events/emitted.ts → 'restaurant.order.placed'

5. Subscribe to events from other plugins
   events/subscribed.ts → 'billing.payment.succeeded'

6. Write migrations
   database/migrations/001_create_menu_items.sql

7. Register permissions
   permissions/permissions.json

8. Add translations
   translations/en.json
   translations/ar.json

9. Write tests
   tests/unit/
   tests/integration/

10. Done
    orbitox doctor --plugin ./plugins/menu-management  # validates everything
    orbitox publish   # publish to marketplace or deploy to platform
```

## The "Can This Be a Plugin?" Test

When a feature request comes in, always ask:

> "Is this feature specific to one product, or would multiple products benefit from it?"

| Feature | Specific | Reusable as Plugin? |
|---------|----------|-------------------|
| Attendance tracking | No — HR + School + Restaurant all need it | ✅ Build as `@orbitox/attendance` |
| KDS (Kitchen Display) | Yes — restaurant only | 🖊 Build as restaurant plugin |
| Leave management | No — HR, School, Hospital all need it | ✅ Build as `@orbitox/leave-management` |
| Kanban board | No — CRM, project management, etc. | ✅ Build as `@orbitox/kanban` |
| Patient triage | Yes — hospital only | 🖊 Build as hms plugin |
| Commission calculation | No — MLM, Sales, Restaurant, Real Estate | ✅ Build as `@orbitox/commissions` |

Every time you build a reusable plugin instead of a one-off feature, you save weeks of development on every future SaaS that needs the same thing.
